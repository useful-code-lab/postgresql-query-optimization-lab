# 🚀 PostgreSQL Performance Tuning Lab 

## 📌 Общая идея проекта

Этот проект демонстрирует системный подход к диагностике и оптимизации производительности PostgreSQL в облачной среде (Neon.tech). Основной акцент сделан не на теории, а на воспроизводимых сценариях с измеримыми результатами.

Проект имитирует реальную нагрузку (1.5 млн строк) и показывает, как PostgreSQL ведёт себя «из коробки» и после грамотного тюнинга.

---

# 🎯 Ключевые навыки, которые демонстрирует проект

Этот репозиторий фактически покрывает важнейшие аспекты работы с PostgreSQL:

### 1. Чтение и интерпретация EXPLAIN ANALYZE

* понимание cost vs actual time
* различие между Seq Scan / Index Scan / Bitmap Scan
* выявление bottleneck'ов

### 2. Работа с индексами

* B-Tree (классика)
* GIN (для JSONB)
* Partial Index (оптимизация размера и write-performance)

### 3. Управление памятью

* `work_mem`
* влияние на сортировки и hash-операции

### 4. Поведение базы под нагрузкой

* транзакции
* блокировки
* уровни изоляции

# 🧠 Разбор кейсов оптимизации

## 🔴 Кейс 1: Seq Scan → Index Scan

### Проблема

Запрос:

```sql
SELECT * FROM orders WHERE user_id = 123;
```

Без индекса PostgreSQL выполняет:

```
Seq Scan on orders
```

👉 Это означает:

* чтение ВСЕЙ таблицы (1.5 млн строк)
* линейная сложность O(n)

---

### 💡 Решение

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

---

### ✅ Что изменилось

| До       | После      |
| -------- | ---------- |
| Seq Scan | Index Scan |
| ~150 ms  | ~0.1 ms    |

📈 Ускорение: ~1500x

---

### 🧠 Важно понимать

PostgreSQL выбирает Seq Scan, если:

* индекс отсутствует
* или planner считает его невыгодным (например, низкая селективность)

---

## 🔴 Кейс 2: External Merge (сортировка на диске)

### Проблема

```sql
SELECT * FROM orders ORDER BY amount DESC LIMIT 100000;
```

В плане:

```
Sort Method: external merge Disk
```

👉 Это значит:

* памяти не хватило
* PostgreSQL использует временные файлы
* происходит I/O → сильное замедление

---

### 💡 Решения

#### Вариант 1 — увеличить память

```sql
SET work_mem = '64MB';
```

📌 Работает на уровне СЕССИИ (это важно!)

---

#### Вариант 2 — использовать индекс

```sql
CREATE INDEX idx_orders_amount_desc ON orders(amount DESC);
```

👉 PostgreSQL может:

* избежать сортировки вообще
* читать данные уже отсортированными

---

### ✅ Результат

| До                    | После           |
| --------------------- | --------------- |
| External Merge (Disk) | Quicksort (RAM) |
| Медленно              | ~10x быстрее    |

---

### 🧠 Глубокий инсайт

`work_mem` применяется:

* **на каждый узел операции**
* и **на каждый поток**

👉 Ошибка новичков:
увеличить `work_mem` глобально → получить OOM

## 🔴 Кейс 3: Partial GIN Index для JSONB

### Проблема

```sql
CREATE INDEX idx_metadata ON orders USING GIN(metadata);
```

👉 Минусы:

* огромный размер
* медленные INSERT/UPDATE

---

### 💡 Решение — частичный индекс

```sql
CREATE INDEX idx_metadata_active 
ON orders USING GIN(metadata)
WHERE status != 'completed';
```

---

### ✅ Что это даёт

* индекс хранит только «активные» записи
* меньше размер
* быстрее записи

---

### 📊 Результат

| До             | После             |
| -------------- | ----------------- |
| Seq Scan       | Bitmap Index Scan |
| Большой индекс | Компактный        |

📈 Ускорение: ~80x

---

### 🧠 Когда использовать Partial Index

Используйте, если:

* данные имеют "естественные сегменты" (status, type, state)
* часто фильтруете по условию
