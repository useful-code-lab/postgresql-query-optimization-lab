# 🚀 PostgreSQL Query Optimization Lab

Практический лабораторный проект для тех, кто хочет **научиться находить и устранять причины медленной работы PostgreSQL**.

Здесь можно не просто прочитать про оптимизацию SQL, а посмотреть на реальные сценарии: взять запрос, измерить его производительность, изучить `EXPLAIN ANALYZE`, найти узкое место и применить оптимизацию, после чего сравнить результат.

Проект построен вокруг базы примерно на **1,5 млн строк** и воспроизводимых экспериментов с PostgreSQL.

---

## 🎯 Что вы получите от проекта

После изучения примеров вы сможете лучше понимать:

* почему PostgreSQL выбирает `Seq Scan`, а не индекс;
* когда `Index Scan` действительно ускоряет запрос;
* как находить медленные операции через `EXPLAIN ANALYZE`;
* почему сортировка может уходить на диск;
* как `work_mem` влияет на сортировки и hash-операции;
* когда стоит использовать B-Tree, GIN и Partial Index;
* как уменьшить объём данных, обрабатываемых запросом;
* почему большой индекс не всегда является хорошим решением;
* как PostgreSQL ведёт себя при конкурирующих транзакциях;
* откуда берутся блокировки и deadlock;
* как проверять результат оптимизации цифрами, а не предположениями.

Главная идея проекта:

> **Не угадывать, почему SQL работает медленно, а измерять, находить узкое место и проверять результат после изменения.**

# 🔍 Что можно практиковать

## 1. Поиск причины медленного SQL

Начните с:

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 123;
```

Посмотрите, какой план выбрал PostgreSQL и сколько времени заняло выполнение.

Без подходящего индекса запрос может использовать:

```text
Seq Scan on orders
```

Это означает последовательное чтение таблицы.

Добавляем индекс:

```sql
CREATE INDEX idx_orders_user_id
ON orders(user_id);
```

После повторного запуска план может измениться на:

```text
Index Scan
```

### Что это даёт на практике

Вы учитесь видеть связь между:

```text
запрос → план выполнения → узкое место → оптимизация → новый план → измеримый результат
```

В демонстрационном сценарии время запроса изменяется примерно со **150 ms до 0.1 ms**.

> Фактический результат зависит от оборудования, версии PostgreSQL, размера данных, статистики и конфигурации.

# ⚡ 2. Оптимизация сортировки

Запрос:

```sql
SELECT *
FROM orders
ORDER BY amount DESC
LIMIT 100000;
```

может привести к:

```text
Sort Method: external merge Disk
```

Это означает, что операции сортировки не удалось полностью выполнить в памяти и PostgreSQL использовал временные файлы.

Один из вариантов эксперимента:

```sql
SET work_mem = '64MB';
```

Другой вариант — создать индекс:

```sql
CREATE INDEX idx_orders_amount_desc
ON orders(amount DESC);
```

Теперь можно исследовать, способен ли PostgreSQL получить данные уже в нужном порядке и избежать дорогостоящей сортировки.

### Чему учит этот пример

Не просто увеличивать память, а понимать:

* сколько данных сортируется;
* где происходит сортировка;
* используется ли диск;
* может ли помочь индекс;
* какой вариант действительно быстрее.

### Важный момент

`work_mem` применяется к отдельным операциям выполнения запроса. Поэтому бездумное глобальное увеличение значения может привести к чрезмерному потреблению памяти при высокой параллельной нагрузке.

# 🧩 3. Оптимизация JSONB с помощью Partial GIN Index

Для JSONB можно использовать GIN:

```sql
CREATE INDEX idx_metadata
ON orders USING GIN(metadata);
```

Но индексирование всей таблицы не всегда необходимо.

Если приложение преимущественно работает с активными заказами, можно исследовать частичный индекс:

```sql
CREATE INDEX idx_metadata_active
ON orders USING GIN(metadata)
WHERE status != 'completed';
```

Такой подход позволяет изучить компромисс между:

* размером индекса;
* скоростью поиска;
* стоимостью `INSERT` и `UPDATE`;
* количеством индексируемых строк.

### Практическая польза

Этот пример помогает понять, почему вопрос:

> «Какой индекс создать?»

часто должен звучать как:

> «Какие данные действительно нужно индексировать для конкретных запросов?»

# 🔒 4. Конкурентные транзакции и блокировки

Проект также показывает сторону PostgreSQL, которую невозможно понять только на примерах обычных `SELECT`.

Например:

```sql
SELECT *
FROM orders
WHERE id = 1
FOR UPDATE;
```

А параллельная транзакция выполняет:

```sql
UPDATE orders
SET amount = 999
WHERE id = 1;
```

На этом сценарии можно исследовать:

* блокировки;
* ожидающие запросы;
* `pg_locks`;
* `pg_stat_activity`;
* `FOR UPDATE`;
* уровни изоляции;
* deadlock;
* влияние конкуренции на производительность.

# 📊 Сравнение до и после

| Сценарий              | До        | После               | Что изучаем         |
| --------------------- | --------- | ------------------- | ------------------- |
| Поиск по `user_id`    | Seq Scan  | Index Scan          | B-Tree              |
| Большая сортировка    | Disk Sort | RAM / Index         | `work_mem`, индексы |
| Поиск в JSONB         | Seq Scan  | Bitmap Index Scan   | GIN, Partial Index  |
| Конкурентные операции | ожидание  | контроль блокировок | транзакции          |

В демонстрационных тестах можно увидеть существенное ускорение отдельных запросов:

* поиск по `user_id` — примерно до **1500×**;
* оптимизация сортировки — примерно до **10×**;
* JSONB-сценарий — примерно до **80×**.

Эти значения являются результатами конкретных экспериментов, а не универсальной гарантией для любой PostgreSQL-базы.

# 🛠 Как использовать репозиторий

Проект можно использовать как практическую лабораторию:

### 1. Запустить исходный сценарий

Получить исходный план и время выполнения.

### 2. Найти узкое место

Изучить:

```sql
EXPLAIN ANALYZE
```

и определить, какая операция занимает основное время.

### 3. Применить оптимизацию

Попробовать:

* индекс;
* Partial Index;
* GIN;
* изменение `work_mem`;
* изменение структуры запроса.

### 4. Повторить измерение

Сравнить новый план с исходным.

### 5. Сделать вывод

Определить, действительно ли изменение помогло и какой ценой.
